## 対象

`*.py`（10 本の Lambda + 共通モジュール）、`Dockerfile`、`ruff.toml`。
設計の背景は `README.md` に記載しています。

## 何をするコードか

AWS のマルチリージョン DR（東京 ⇔ 大阪、Warm Standby）の切替を
Step Functions で実行する。その中から呼ばれる Lambda 群。

- 操作系 3 本 … 旧 ACTIVE 側の閉塞、新 ACTIVE 側の開放
- 観測系 7 本 … 新 ACTIVE 側が受けられる状態かの確認

## 環境・制約

- Python 3.13、コンテナイメージでデプロイ（Layer は使わない）
- 10 本で同一イメージを共有し、`image_config.command` でハンドラを切り替える
- 外部ライブラリは `kubernetes` のみ。**Powertools は採用しない**
  （Logger 以外に使う機能がなく、依存を増やす価値がないと判断済み）
- boto3 は Lambda ランタイム同梱
- Terraform で管理。設定は環境変数で注入

### 制御の設計（特に重点的に見てほしい）

1. **正常性確認の待機を Step Functions の `Retry` で実現している。**
   観測系 Lambda は「まだ収束していない」状態で `RetryableError` を送出し、
   ASL 側は `Retry` の `MaxAttempts` を待機上限として使う。
   `Wait` + `Choice` のポーリングループは使っていない。
   → 「まだ準備できていない」を例外で表現するのは適切か。
2. **旧 ACTIVE 側の閉塞失敗を許容して切替を続行する**（`ContinuableError`）。
   リージョン障害中は相手のコントロールプレーンが応答しないため。
   → スプリットブレイン防止の観点で、無条件に続行してよいか。
3. **「止めるべきエラー」に例外型を定義していない。** Retry にも Catch にも
   マッチしない例外は Step Functions がワークフローを失敗させるため。
   → 意図が読み取りにくくないか。明示的な型を持つべきか。
4. **正常性確認の内容**が、各リソースのコントロールプレーン状態の確認に
   偏っている（API GW のみ実リクエストを 1 発投げる）。
   → 切替可否の判断材料としてこれで十分か。

### 実装の方針

5. 観測系は正常時に何も返さない。問題項目のみ JSON にして例外に載せる
6. AWS 例外の捕捉は `@ops_handler` に集約。個々の操作側では書かない
7. 複数インスタンスのループは Lambda 内（`common.run_per_item`）。
   Step Functions の `Map` は使っていない
8. Lambda はリソース単位に分割（10 本）。1 関数に複数リソースをまとめない
9. `SELF` / `PEER` の対称構造。切替方向は実行するリージョンで決まり、
   入力に `direction` を持たない
10. EKS への接続は `aws eks update-kubeconfig`（既存 Lambda との統一を優先）
